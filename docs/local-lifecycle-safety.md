# LOCAL 회원 수명주기 안전장치 — 개발 중, 운영 미연결

## 현재 범위

별도 `feature/local-erasure-maintenance-safety` 작업 브랜치에서 진행한다. 원래 작업 공간의 미추적 파일을 덮어쓰지 않고 기존 종료 후보 판정 코드/시험을 복사해 재검증했다. 운영 배포, 파기 실행, GitHub 체크포인트 기록 변경은 하지 않았다.

## 확인된 간극

- `ProtectedErasureLedgerFactory`의 MySQL 자문 잠금은 `ensureRecorded` 구간만 감싼다. 파기 트랜잭션 커밋, 완료 증거 기록, 외부 Python 복원 절차 전체를 보호하지 않는다.
- `FileErasureObjectStore`의 `.ledger.lock`은 개별 파일 동작 잠금이다. 여러 파일/DB/독립 체크포인트에 걸친 일관된 작업 단위 잠금과 다르다.
- 현재 복원 검증은 컨테이너의 쓰기 중지 플래그를 검사한다. 새 잠금만 추가했다고 그 검사를 제거하면 안 된다.
- `GitHubErasureCheckpointStore`는 기록 시 건수 `+1`, 읽기 시 건수 감소 불가를 강제한다. 현행 검증을 느슨하게 바꿔 삭제를 허용하면 소실 탐지가 무너진다.

## 공통 잠금 기초 구현

`LocalMaintenanceLease`는 Linux POSIX 레코드 잠금을 사용한다. 사전 생성된 private 디렉터리의 0600 단일 링크 일반 파일 `.maintenance.lock`만 사용하며 파일 자동 생성/삭제/교체는 하지 않는다. Python 참여자는 `fcntl.lockf`를 써야 한다. 기존 백업 폴더 잠금 `flock`은 계속 별도로 유지한다.

Java/Python 상호 차단, 프로세스 강제 종료 시 해제, 같은 JVM의 중복 요청으로 첫 잠금이 해제되지 않음, 누락/공개 권한/내용 있는 파일/링크 거절을 합성 테스트로 확인했다.

후속 구현에서 `AccountMaintenanceGuard`를 배치 `AccountErasureWorker`에 연결했다. 획득은 트랜잭션 시작 전, 해제는 `TransactionTemplate.execute`가 커밋/롤백을 마친 후이다. 외부 트랜잭션 참여는 거절한다. H2 합성 데이터로 커밋/롤백 시점·잠금 충돌·중첩 트랜잭션 차단을 확인했다. 운영에는 배포하지 않았다.

잠금 파일은 대장 데이터 디렉터리와 **별도 경로** `/home/luha/geupddong-maintenance/.maintenance.lock`로 설계했다. 기존 대장 스캐너가 알 수 없는 파일로 거절하는 문제를 피하고, 대장 저장 형식 검사를 완화하지 않는다. 이 경로는 아직 운영에 생성하지 않았다.

활성화하려면 `ERASURE_MAINTENANCE_LOCK_ENABLED=true`, `ERASURE_MAINTENANCE_DIRECTORY=/home/luha/geupddong-maintenance`와 LOCAL 대장 설정이 모두 일치해야 한다. 전체 참여자 배포/검증 전에는 값을 켜지 않는다. 배치만 먼저 켜도 전체 동시 실행 안전성이 확보되지는 않는다.

### 연결 시 지킬 순서

1. 백업/복원 운영 도구는 기존 백업 잠금 → 공통 maintenance 잠금 순서로 획득한다.
2. 회원 변경자는 maintenance 잠금 → SQL 트랜잭션 → 회원/탈퇴 행 잠금 → 기존 checkpoint 잠금 순서로 실행한다.
3. maintenance 잠금은 메서드 본문뿐 아니라 **트랜잭션 커밋/롤백 완료까지** 유지한다. `@Transactional` 메서드 안에서 단순 try/finally 해제로 끝내지 않는다.
4. 완료 증거 기록자도 동일 잠금에 참여한다. 인수검사/복원도 동일한 inode를 사용해야 한다.
5. 복원 동안 장시간 대기시키지 않고 잠금 충돌은 재시도 가능한 보류로 반환한다. 적용 전 API 오류 매핑 및 배치 재시도 회귀시험이 필요하다.
6. 배포 과정에서 잠금 파일이 바뀌면 보호가 분리되므로, 설치/마운트/재배포 검사와 동일 inode 검증까지 완료해야 한다.

## 대장 종료 후보 판정

`ErasureRetirementPlanner`는 완료 영수증·DB 세대·회원 식별·독립 체크포인트·최신 증거를 결합한다. 최소 검토 대기 32일과 모든 사본 제거 등 8가지 증거를 확인한다. 결과는 `REVIEW_CANDIDATE` 또는 명시적 보류이며 실제 삭제 권한이 아니다. 기존 안전 검토 기간을 법정 기간이라고 주장하거나 이번에 수정하지 않았다.

## 종료 실행 프로토콜 설계 — 아직 미구현

기존 v1 reader/writer의 엄격한 검사를 유지하며, 별도로 검증 가능한 종료 작업 계약이 필요하다.

1. 공통 잠금 아래 최신 증거·후보 계획·기존 체크포인트를 다시 확인한다.
2. exact 대상/암호문 해시와 단계가 담긴 암호화된 비공개 복구 기록을 내구성 있게 남긴다. 공개 독립 기록에는 회원별 목록을 넣지 않는다.
3. 독립 기록에 준비 상태를 확인받는다. 준비 상태를 모르는 구버전 소비자는 실패 시 중단해야 하며 혼합 버전 활성화는 금지한다.
4. 준비 상태에서는 회원 파기/복원을 막고, 승인된 intent/catalogue/completion 파일만 단계별 제거한다.
5. 검증된 잔여 inventory를 포함한 종료 완료 체크포인트를 CAS로 기록한다. 단순 count 감소 허용이 아니라 이전 준비 상태와 대상 집계에 결합된 전이만 허용한다.
6. 기록 중단/응답 불명확이면 새 삭제를 시작하지 않고 원래 작업만 검증해 재개한다. 이미 삭제된 파일을 추정 복원하거나 기준 건수를 임의 초기화하지 않는다.
7. 완료 후 개인별 복구 기록 자체도 정리하고 비식별 집계 증거만 유지한다. 복구 기록을 무기한 보관하는 우회는 금지한다.

## 완료 전 필수 작업

- 공통 잠금을 API·배치의 실제 트랜잭션·완료 증거·Python 복원에 연결하고 격리 DB에서 교차 실행 시험.
- 종료 프로토콜의 저장 형식/전이 검증/실패 재개 구현 및 테스트. 현재 후보 판정만으로 종료를 실행하면 안 된다.
- 새 형식의 API·배치·운영 도구 동시 호환과 배포/복구 인수 계획.
- 과거 Redis/기타 사본 정리, binlog 정책 실제 이행, 모든 사본 범위 확인.
- 운영 변경 승인 및 첫 정기 실행 인수.

따라서 2단계 전체 또는 탈퇴·복구 활성화 준비 완료로 표시하지 않는다.

# 실제 사본 점검 인수표

이 문서는 결과를 자동 승인하지 않는다. unknown인 항목을 임의로 확인 완료 처리하면 안 된다.
실제 서버 주소·보관 경로·키·member ID는 비공개 점검 기록에만 남긴다.

## 판단 순서

1. 점검 범위의 경로·볼륨·외부 저장소·수동 다운로드 목록을 확정하고 범위 해시를 만든다.
2. 전체 목록을 실제로 조사한다. 접근 실패·누락·미확인 사본이 있으면 보류한다.
3. 각 종류별로 어떤 시점 이전의 사본이 더는 존재하지 않는지 증명한다.
4. DB server UUID·복원 세대·최근 복원 시점, 암호키 복구 점검 시점을 결합한다.
5. 운영자가 결과를 검토하고 승인한 후에만 seal-reviewed를 실행한다.
6. 10분 이내 dry-run → 결과 확인. 쓰기 플래그 활성화는 별도 승인이다.

| 범위 | 반드시 확인 | 부적절한 대체 근거 |
| --- | --- | --- |
| DUMPS | 모든 dump와 암호화 사본, 검증 메타데이터, 보관 종료 결과 | 현재 폴더 1개가 비어 있음 |
| BINLOGS | 실제 남은 이벤트 범위와 자동 만료 이행 | 30일 설정 또는 파일 mtime만 확인 |
| REDIS_DISK | 현재 설정과 현재/과거 RDB·AOF 파일 부재 | 현재 save/appendonly 설정만 확인 |
| LEGACY_VOLUMES | 활성·비활성 볼륨과 수동 복제본 전체 | 컨테이너 목록에 안 보임 |
| RESTORE_TEMP | 복원 임시 DB·덤프·실패 후 잔여물 | 마지막 복원 작업이 성공함 |
| OFFHOST_COPIES | 이전 외부 저장소·수동 다운로드 등 전체 범위 | 새 구현이 LOCAL이라는 사실 |

## 기존 점검 도구의 한계

기존 남은 사본 점검은 Redis 파일·백업 트리의 제한된 메타데이터를 보고한다.
기존 binlog 점검은 설정·파일 크기·mtime을 보고하며 enforcementVerified=false,
allCopiesCleared=false를 명시한다. 이 출력을 true로 바꾸어 새 실행기에 넣으면 안 된다.
이벤트 범위 증명과 점검 범위 확정이 먼저다.

새 Java 실행기는 이러한 한계를 우회하지 않는다.
확인한 사본 종료 기준 시점과 회원 부재 확인 시점을 비교하고 충분하지 않으면 보류한다.
현재 운영 값이 비어 있거나 자료가 오래되었다면 시스템이 정상적으로 보류해야 한다.

## 배포 인수 시 함께 확인

- 동일한 maintenance 잠금이 실제 복원·백업·API·배치 모두에 연결돼 있는가.
- 기존 인증 파일과 암호키를 비밀 출력 없이 읽을 수 있는가.
- 완료 증거의 최초 확인 시점을 재시도에서 앞당기지 않는가.
- 검토 pending 파일·오래된 저널·독립 응답 불명확 상태가 없는가.
- 보류 알림을 누가 확인하고, 10분 유효 자료를 언제 다시 발급할 것인가.

대장 종료를 자동으로 켠 뒤 검토 자료를 수동으로 한 번만 발급하면 장기 운영이 완성되지 않는다.
자료 갱신 주체·주기·전체 범위 검증을 운영 절차로 확정해야 한다.

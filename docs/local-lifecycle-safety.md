# LOCAL 회원 수명주기: 잠금·완료 증거·대장 종료

기준일 2026-09-10. 구현·검증 상태이며 운영 활성화 완료 보고가 아니다.
최신 체크리스트는 [활성화 준비표](retirement-activation-readiness.md)를 따른다.
이전 단계별 미구현 설명은 이 문서로 통합했다. 과거 설명은 Git 이력에서 확인한다.

## 서로 다른 작업

| 작업 | 목적 | 대상 |
| --- | --- | --- |
| 회원 자동 파기 | 탈퇴 보관 기간 종료 후 회원정보 제거 | MySQL 회원·관련 세션 |
| 완료 증거 기록 | DB 실제 부재의 최초 확인 시점 기록 | 암호화 completion |
| 대장 종료 | 과거 사본의 복원 위험 해소 후 대장까지 제거 | intent·catalogue·completion·복구 저널 |

대장 종료의 32일 검토 대기와 사용자 탈퇴·복구는 별개다.
32일은 기존 안전 검토 기준이며 법정 보관 기간이라고 주장하지 않는다.
기간 경과만으로 삭제하지 않으며 사본 증거가 없으면 보류한다.

## 일일 순서와 잠금

공공데이터 수집 → 회원 자동 파기 → 완료 증거 재확인 → 대장 종료 검토 순으로 실행한다.
앞 단계 실패 뒤에도 다음 단계의 자체 보호 검사를 시도하지만 실패가 삭제 허가로 바뀌지는 않는다.
완료 증거 기록은 사본 제거를 증명하지 않으며 copyClearance=false를 로그에 명시한다.
대장 종료는 기본 비활성, 1회 상한 기본 10건(허용 1~100)이다.

API·배치·복원은 사전 생성한 같은 maintenance 잠금 파일을 쓴다.
Linux POSIX 레코드 잠금이며 Python은 lockf를 쓴다. 기존 백업 폴더 잠금과 별개다.
0600 단일 링크 일반 파일·0700 상위 폴더를 요구하며 잠금 파일 삭제·교체·자동 재생성을 금지한다.
순서는 백업 잠금(해당 시) → maintenance → SQL 트랜잭션 → 행 잠금 → checkpoint 잠금이다.
DB 커밋·롤백까지 maintenance를 유지한다.
공통 잠금 준비 배포는 API #98·배치 #46에서 수행했다. 이번 종료 실행기는 별도 배포 대상이다.

## 종료와 중단 복구

실제 암호문·회원 식별·DB 세대·checkpoint·후보 계획을 결합하고 회원 1명의 복구 자료를
별도 private 폴더에 AES-256-GCM으로 저장한다. 파일 8KB 제한과 파일/디렉터리 fsync·인증 재독을 적용한다.
이메일·닉네임은 없지만 식별 키가 있으므로 복구 저널도 개인정보 보호 대상이다.
삭제한 원본을 디스크에 되살리지 않고 메모리에서 원래 계획을 검증한다.

| 독립 단계 | 의미 | 일반 대장 기록·복원 |
| --- | --- | --- |
| 0 | 계획·집계·암호화 저널 준비 확인 | 차단 |
| 1 → 2 | intent 삭제 준비 → 확인 | 차단 |
| 3 → 4 | catalogue 삭제 준비 → 확인 | 차단 |
| 5 → 6 | completion 삭제 준비 → 확인 | 차단 |
| 7 | 감소 checkpoint와 종료 증거를 동일 Git commit으로 기록 | 차단 |
| 8 | 복구 저널 제거·디렉터리 fsync 확인 | 새 호환 소비자 허용 |

암호문 SHA-256과 독립 준비 단계를 모두 확인해야 삭제한다.
이미 없는 파일은 동일 준비 단계의 재시도에서만 허용한다.
보존 대상 변경·누락, 완료 대상 재등장, 잘못된 키·세대·계획, 응답 불명확은 보류한다.

10분 만료 후에는 최신 DB·사본 증거를 다시 확인하고 불변 review 기록을 추가한 명시적 재개만 허용한다.
원래 계획과 저널은 덮어쓰지 않는다. 7단계 이후 저널 정리는 만료 후에도 가능하다.
삭제 확인 유실은 부재와 fsync를 재확인한다. 8단계 후 저널 재등장은 조용히 삭제하지 않는다.
외부 준비 전에 남은 orphan 저널은 원래 revision·checkpoint·모든 원본 암호문이 그대로인 경우의
명시적 서비스 경로에서만 정리할 수 있다. 일반 CLI는 자동 정리하지 않는다.

## 독립 이력·호환

GitHubErasureHistoryStore는 순번별 정상 checkpoint·종료 phase·재검토 review를 검증한다.
연속 종료와 중간 정상 추가를 지원한다. 기존 checkpoint 형식과 v1 건수 감소 차단을 느슨하게 하지 않았다.
0~7단계는 새 소비자도 차단하고 구버전 소비자는 새 형식 전체를 거절한다.

단일 revision tree, 연속 순번, 이전 해시, 세대·시간·건수·작업 일치를 확인한다.
Git ref는 force=false로 갱신하고 결과를 재독한다. 충돌 시 강제 갱신하지 않는다.
불변 blob만 최대 2,048개 캐시하고 branch head·인가 상태는 캐시하지 않는다.
이력 누적에 따른 최초 전체 조회 비용은 운영 규모에서 별도 측정해야 한다.

API·배치·복원 CLI·사전검사와 별도 BackupLedgerReplay를 새 reader로 연결했다.
구버전 롤백을 위해 이력 파일 삭제나 기준 건수 초기화를 하면 안 된다.
초기 실험용 GitHubRetirementRecoveryStore와 순수 전이 검증기는 런타임 경로가 아니다.

## 실제 사본 증거

현재 DB server_uuid·DB명·회원 부재를 SELECT로 확인한다.
ID가 재사용되어 어떤 회원 행이라도 존재하면 차단한다.
검토 파일은 다음 범위 전체의 제거 확인 기준 시점과 scope 해시를 포함해야 한다.

- DUMPS: 현재·과거 덤프와 암호화 사본.
- BINLOGS: 실제 남은 변경 로그.
- REDIS_DISK: 현재·과거 RDB/AOF.
- LEGACY_VOLUMES: 과거 볼륨·수동 복제 데이터.
- RESTORE_TEMP: 복원 임시 DB·덤프.
- OFFHOST_COPIES: 외부 저장소·수동 다운로드 등 전체 외부 사본.

빈 폴더나 보관 설정만으로 사본 부재를 추정하지 않는다. 알 수 없는 항목은 보류한다.
삭제 완료 시점 이전 사본을 모두 배제해야 한다. 이후 DB 복원이 있었다면 자동 확정하지 않는다.
검토 파일은 10분 이내, 암호키 복구 검증은 24시간 이내여야 한다.

RetirementAuditSealCli --seal-reviewed는 사람이 검토한 자료를 인증 암호화하는 도구이지,
사본을 조사하거나 근거를 자동 승인하는 도구가 아니다.
승인 플래그·private 파일·세대·서버·scope를 검사하고 공통 잠금 아래 원자 교체한다.
부분 pending 파일이나 인증 불가 기존 파일은 덮어쓰지 않는다.
실제 운영 점검과 이 자료 갱신 절차의 인수는 남아 있다.

## 안전 경계

- 점검 모드와 기존 비활성 플래그 유지.
- 실제 회원·제보·운영 백업·binlog를 시험 목적으로 변경하지 않음.
- API → 배치 → 복원/점검 도구 호환 배포와 실접속 검증 전에 운영 종료 기록을 쓰지 않음.
- 기능 구현과 별개로 전체 CI·실제 사본 점검 인수·운영 활성화 승인 필요.
- 사용자 탈퇴·복구와 대장 종료를 무조건 한꺼번에 켜지 않고 각 필수 조건을 따로 확인.

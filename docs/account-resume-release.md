# 회원 탈퇴·복구 재개 후보

이 PR은 준비 코드와 검사이며 운영 활성화가 아니다. 전체 제보·감사·시스템 로그 정리는 포함하지 않는다.

## 두 단계

| 단계 | 회원 탈퇴·복구/파기 | 보호 대장·독립 기준 | 대장 최종 정리 |
| --- | --- | --- | --- |
| guarded | 점검 유지 | 활성화 후보 | 계속 비활성 |
| active | 별도 승인 후 활성화 후보 | 활성 상태 유지 | 계속 비활성 |

`scripts/prepare-local-resume.mjs`는 설정 후보만 생성한다. 서버에 접속하거나 파일을 쓰거나 배포하지 않는다. 현재 운영 workflow와 준비 전용 진입점은 변경하지 않았으며 resume 프로필을 계속 거절한다.

기존 검증기로 LOCAL 식별자·키링·Redis·전송 형식을 확인한다. 새로운 후보에는 원격 R2 설정, 전체 업무 이력 삭제 또는 로그 저장 방식 변경을 넣지 않는다. 출력 payload는 비밀값을 포함할 수 있으므로 로그·PR·문서에 출력하지 않는다.

## 적용 전에 필요한 실제 증거

- 정확한 릴리스 커밋에 대한 승인.
- API/배치의 같은 LOCAL 저장소·키링·복원 세대·공통 잠금 및 Redis 연결.
- 설치된 복원 도구와 최신 검증 스냅샷 일치.
- guarded 상태로 양쪽 구성 적용 후 재검증.
- 확정된 웹 정책의 공지·공개와 실제 처리의 일치.
- 활성화 직전 읽기 전용 파기 대기 건수 확인. 현재 후보는 대상/비정상 레코드가 0이 아닌 경우 거절하며, 기존 대상이 발견되면 별도 검토한다.
- 기존 방식 탈퇴 계정은 자동 전환·복구·삭제하지 않는다.

입력의 VERIFIED/APPROVED 값은 실제 증거를 대신하지 않는다. 설정 후보 생성기만으로 활성화해서는 안 된다.

## 보호 단계의 수동 배포 연결

`account-guarded-transition.yml`은 수동 요청만 받는다. main의 정확한 workflow 커밋과 현재 실행 중인 API/배치 이미지 커밋을 각각 승인 변수로 고정해야 실행된다. 기본 동작은 읽기 전용 check이며, apply-guarded는 별도 운영 승인 및 다른 배포/수동 설정 변경 중지 확인이 필요하다. 기존 deploy.yml의 준비 상태 검사 조건은 완화하지 않았다.

진행 순서: 양쪽 paused → API guarded → 배치 guarded → 정책 공개·시행 → 배치 active → API active. 각 단계는 한 번만 요청한다. 응답이 끊기면 자동 재시도하지 않고 실제 상태부터 확인한다.

## 실제 회원 작업 활성화 연결

`account-active-transition.yml`은 별도 수동 요청과 정확한 workflow/이미지 커밋 승인을 요구한다. 기본은 check이며 실제 apply-active에는 별도 활성화 승인 및 전체 배포 중지 확인이 필요하다.

API/배치에 공통으로 승인한 정책 버전·공지 시각·시행 시각을 고정한다. 호스트는 https://geupddong.com/policies/terms 와 /policies/privacy 의 실제 HTML을 인증정보 없이 읽고 같은 공개 버전·날짜, 눈에 보이는 공지/시행 안내, 검토 초안 문구 부재를 확인한다. 리다이렉트·로그인 화면·다른 버전·중복 표식·미래 시행일·누락된 날짜는 거절한다. 적용 전과 후에도 재확인한다. 공개 확인은 법률상 적정성이나 과거에 실제 공지했다는 사실을 증명하지 않는다. 운영자의 공개 이력·검토 근거는 별도로 남겨야 한다.

웹 피처는 여전히 draft, 날짜 미정이므로 지금 active 사전검사는 통과할 수 없다. 날짜나 공개 상태를 환경 변수 하나로 바꾸지 않고 승인된 웹 소스 릴리스에서 수정한다. 정책 버전은 내용 확인을 마친 정확한 웹 릴리스와 연결하고, 동일 버전으로 다른 내용을 덮어쓰지 않는다.

배치를 먼저 active로 만들어도 API는 guarded여서 신규 탈퇴·복구 접수는 열리지 않는다. 초기 전환 동안 탈퇴 요청 테이블이 0건인지 반복 확인하며, API active 후 첫 계정 요청부터 실제 회원 개인정보 파기가 발생할 수 있다. 모든 서비스 DB 변경이 없다고 설명해서는 안 되며, CLI가 직접 변경 SQL을 실행하지 않는다는 뜻으로만 directDatabaseWrites=false를 사용한다.

호스트 검사는 공통 유지보수 잠금 안에서 실행 이미지·LOCAL 식별자·키링·복원 세대·Redis 연결·최신 24시간 이내 복원 영수증과 대장 스냅샷을 확인한다. account_withdrawal 전체가 0건이어야 하며 기존 기록이 있으면 별도 검토한다. 원본 환경/Compose 변동과 Compose의 설정 덮어쓰기도 검사한다.

승인된 apply는 해당 서비스의 계정 설정 파일만 원자적으로 교체하고 같은 이미지를 재사용한다. 다른 서비스 재생성·이미지 다운로드·DB 직접 변경은 하지 않는다. 기존 설정은 소유자 전용 파일로 보존하며 실패 시 설정 복구와 해당 서비스 재시작까지만 수행한다. 개인정보 파기를 되돌린다는 의미가 아니다. API는 DB 오류여도 HTTP 200이 될 수 있어 정상 응답 본문까지, 배치는 UP 상태까지 확인한다.

주의: 저장소별 Actions 동시 실행 방지는 서로 다른 저장소/수동 배포까지 잠그지 않는다. 운영자의 전체 배포 중지 확인이 필요하다. 기존 준비 전용 배포는 guarded 상태를 거절하므로 보호 단계 적용 후 일반 배포를 재개하려면 후속 호환 배포 경로 검토가 필요하다.

## 상태 보존 이미지 배포 경로

`account-preserving-rollout.yml` / `--phase preserve`를 추가했다. 기존 deploy.yml의 준비 상태 제한은 그대로 두고, 별도로 검토한 수동 배포에서만 사용한다. 두 서비스가 모두 paused, guarded 또는 active인 안정 상태만 허용하며 전환 중 혼합 상태는 거절한다.

- 정확한 workflow 커밋, 현재 양쪽 이미지 커밋, 다음 이미지 소스 커밋과 registry digest를 승인 변수에 고정한다.
- 이미 빌드·검토된 이미지만 사용한다. 기본 check는 내려받기·설정 쓰기·재시작이 없다. 실제 apply-image만 승인 digest로 내려받고 해당 커밋 태그에 연결한다. 이미지 캐시/태그는 변경될 수 있다.
- 기존 Compose의 해당 서비스 image 한 항목만 바뀌는지 최종 렌더 결과를 비교한다. 계정 설정 파일·일반 환경 파일·다른 서비스·회원 기능 스위치는 수정하지 않는다.
- 공통 잠금을 잡은 채 현재 대장/독립 기준을 검증하고 교체 전후 같은지 재검사한다. 정상 서비스 중에는 탈퇴 요청/대장이 0건일 필요가 없으므로 최초 활성화의 0건 규칙을 재사용하지 않는다. 최신 복원 영수증의 24시간 조건은 유지한다.
- DB·대장 형식이 이전 이미지와 호환되는 릴리스만 허용한다. 확인 입력은 마이그레이션 검토 자체를 대신하지 않는다. 비호환 DDL/대장 변경이 포함된 릴리스는 이 경로를 쓰지 않는다.
- 실패 시 Compose와 이미지 설정을 복구하고 재점검을 요구한다. 외부에서 파일이 바뀌었으면 덮어쓰지 않고 중지한다. 이미지 롤백이 DB 변경이나 개인정보 파기를 되돌리지 않는다.

이 경로의 격리 검사와 코드 연결은 준비 작업이다. 실제 운영 이미지 교체 인수는 별도 승인 후 수행하며, 이 문서가 배포 승인이나 임의의 과거 이미지 복귀 허가가 아니다.

2026-09-10 API 첫 단계의 운영 읽기 전용 사전 검사는 통과했다. 설정 파일 교체·컨테이너 재시작·DB/대장 기록은 실행하지 않았다. 배치 두 번째 단계의 실접속 인수는 API 보호 단계 적용 후에만 가능하다.

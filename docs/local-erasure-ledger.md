# 로컬 파일 파기 대장 전환 — 설계 및 인수 기준

작성: 2026-09-09. **로컬 개발 중이며 운영 전환·회원 파기 활성화·R2 삭제를 완료했다는 문서가 아니다.**

## 결정

회원별 파기 의도와 완료 기록은 미니 PC의 전용 로컬 디렉터리에 암호화하여 저장한다. 기존 GitHub 독립 체크포인트(집계 건수·내용 해시·복원 세대)는 유지한다. 개인별 목록을 GitHub에 추가하지 않는다. 이 구조는 외부 **객체 저장소** 의존성을 줄이지만 GitHub 의존성을 없애지는 않는다.

로컬 파일과 로컬 해시만 동시에 과거 상태로 돌아가면 그 자체로 최신 여부를 증명할 수 없다. 따라서 체크포인트를 같은 디스크 파일로 대체하지 않는다. GitHub 조회/확정이 실패하면 파기·복원 검증을 중단한다. 완전한 오프라인 운영이나 악성 관리자에 대한 변조 방지를 보장하지 않는다.

## 범위와 원본 보존

- 기존 API·배치의 `feature/domestic-erasure-storage` 작업에서 시작했고, 기존 미커밋 국내 저장소 설정·테스트·보관 종료 계획기를 보존한다.
- 현재 API·배치 로컬 작업 브랜치: `feature/local-erasure-ledger`. 아직 커밋·push·PR 게시·운영 배포하지 않았다.
- 웹, DB 스키마, 실제 회원정보, 운영 배포, 현재 저장소 데이터는 이번 로컬 구현으로 변경하지 않는다.
- 기본 provider는 여전히 R2이고, 파기 대장의 enabled 기본값과 LOCAL 인수 확인 기본값은 false다. LOCAL 선택 실패 시 R2로 자동 우회하지 않는다.
- 기존 `v1`, `catalogue-v1`, `completion-v1` 문서와 AES-256-GCM 인증 형식을 그대로 재사용한다. 키는 대장 디렉터리에 저장하지 않는다.
- 추가 SQLite 서버/라이브러리는 도입하지 않았다. 기록 단위가 작은 불변 객체이므로, 기존 문서 포맷과 재시도 검증을 재사용하는 write-once 파일 구현을 선택했다. 부분 파일은 덮어쓰지 않고 보류한다.

## 처리 순서

1. API·배치가 공유하는 기존 DB 잠금으로 파기 대장 갱신을 직렬화한다.
2. 최신 독립 체크포인트와 로컬 카탈로그/파기 의도 목록을 비교한다. 일치하지 않는 회원을 임의로 정상화하지 않는다.
3. 카탈로그와 파기 의도를 각각 `CREATE_NEW`로 기록한다. 파일 디스크 반영과 디렉터리 디스크 반영을 확인한다.
4. 기존 파일이라도 다시 디스크 반영을 요청하고 복호화·동일 내용을 확인한다. 암호화 nonce가 달라지므로 암호문 동일성으로 재시도를 판단하지 않는다.
5. 전체 목록을 재검증하고 독립 체크포인트를 확정한다. 여기까지 성공해야 기존 Redis/SQL 파기 로직이 계속된다.
6. 완료 기록은 최초 확인 시점을 유지하는 별도 불변 파일로 저장한다.

저장소와 DB는 하나의 트랜잭션이 아니다. 카탈로그만 기록된 경우 등 부분 성공은 기존 동일 요청 재시도 규칙으로 재조정한다. 파일 중간 쓰기 실패로 인증할 수 없는 파일이 생겼다면 자동으로 지우거나 덮어쓰지 않는다. 그 요청은 보류하고, 관련 DB/체크포인트/카탈로그를 확인하는 별도 복구 절차가 필요하다.

## 디렉터리와 권한

운영 경로는 아직 설치하지 않았다. 승인 시 컨테이너의 임시 레이어가 아닌 호스트의 전용 디렉터리를 API·배치·오프라인 검증 도구에 연결한다. DB 데이터·DB 백업 복원 대상과 겹치지 않아야 한다.

- Linux 전용; 현재 허용 파일시스템: ext4/ext3/xfs/btrfs. tmpfs, NFS/SMB, overlay, 미검증 파일시스템은 차단한다.
- 디렉터리 0700, 파일 0600. API·배치의 파일 접근 UID를 일치시키고 실제 서비스 계정으로 검증해야 한다.
- 심볼릭 링크, 하드링크, 잘못된 파일명, 다른 realm, 알 수 없는 디렉터리 항목을 거부한다.
- `.ledger-store`: 형식 버전, realm, 저장소 UUID. UUID는 승인된 설정의 `local-store-id`와 일치해야 한다.
- `.ledger.lock`: 이미 존재해야 하는 프로세스 간 파일 잠금. 삭제/재생성으로 잠금을 우회하지 않는다.
- 의도 파일: `v1__<realm>__<withdrawal-uuid>.bin`
- 카탈로그 파일: `catalogue-v1__<realm>__<withdrawal-uuid>.bin`
- 완료 파일: `completion-v1__<realm>__<database-epoch>__<withdrawal-uuid>.bin`

최초 프로비저닝은 운영자 승인 절차로 디렉터리·마커·잠금 파일을 만들고 디스크 반영해야 한다. 애플리케이션이 누락된 디렉터리나 마커를 자동 생성하지 않는다. 초기 빈 대장의 적법성/완전성은 마커가 아니라 기존 독립 체크포인트와 기존 저장소 대조로 확인한다.

## 설정(아직 운영에 적용하지 않음)

2026-09-09 읽기 전용 운영 점검 후 후보를 구체화했다: 호스트/컨테이너 동일 경로 `/var/lib/geupddong-erasure-ledger`, 기존 운영 도구와 같은 UID/GID 1000:1000, 0700/0600. 현재 API·batch JVM은 0:0이므로 별도 승인 배포에서 사용자 변경이 필요하다. 기존 batch region-results는 이미 1000:1000 소유다. 후보 경로는 아직 없고 생성하지 않았다.

`deploy/local-ledger.override.yml`에 경로 자동 생성 금지(`create_host_path: false`)와 UID를 명시한 준비 템플릿을 추가했다. `scripts/prepare-local-ledger.mjs`는 `local-paused` 명시 선택과 별도 승인값을 요구하며, 대장/계정 기능은 비활성 상태로만 설정을 생성한다. 실제 파일시스템 검증·운영 배포·활성화를 대신하지 않는다. 기존 배포 워크플로는 아직 이 프로필로 전환하지 않았다. API·batch 설정 회귀 시험은 각각 17건 통과했다.

| 설정 | 의미 |
| --- | --- |
| `ERASURE_LEDGER_PROVIDER=LOCAL` | 로컬 파일 구현 명시 선택 |
| `ERASURE_LEDGER_LOCAL_ACCEPTANCE_VERIFIED=true` | Linux 및 실제 서비스 UID 인수 후에만 허용 |
| `ERASURE_LEDGER_LOCAL_DIRECTORY` | 사전 생성된 절대 경로 |
| `ERASURE_LEDGER_LOCAL_STORE_ID` | 마커와 일치하는 저장소 UUID |
| `ERASURE_LEDGER_CATALOGUE_ENABLED=true` | 로컬 모드 필수 |
| 기존 realm/active-key-id/keys-json | 기존 인증 암호화 포맷 유지 |
| 기존 checkpoint enabled/token/database epoch | 운영 파기에서 계속 필수 |

LOCAL은 R2 bucket/endpoint/access-key를 읽거나 클라이언트를 생성하지 않는다. 원격 저장소 관련 기존 설정은 전환 검증 전 임의로 제거하지 않는다. API·배치·오프라인 도구 모두 동일한 provider/realm/키/저장소 경로를 사용해야 한다.

## 복원 차단

`AccountErasureRestoreCli`는 기존 격리 DB/작업 중지 조건에 더해 `VerifiedErasureSnapshot`을 사용한다. 입력된 expected count만으로 복원을 허용하지 않는다.

1. GitHub에서 독립 체크포인트를 읽어 realm, 복원 세대, 미래 시각 여부를 확인한다.
2. 로컬 의도와 카탈로그 전체를 읽어 개수, 사용자 중복, 문서 정체성, 전체 내용 해시를 대조한다.
3. 체크포인트를 다시 읽어 검증 도중 변경되지 않았는지 확인한다.
4. 검증을 모두 마친 목록만 격리된 복원 DB 재파기에 전달한다.

이 도구는 운영 DB 승격을 실행하지 않는다. 운영 승격 전에는 여전히 writers 정지, 복원 DB 재파기 후 검사, Redis 세션 무효화, 검증 이후 변경 없음 확인이 필요하다. `writers stopped=true`는 자동 잠금 취득이 아니라 운영 절차 확인값이다.

**디스크/키/대장 유실 또는 최신 여부 미확인 시 과거 회원 DB를 운영에 복원하지 않는다.** 화장실 같은 공개 데이터와 회원 데이터의 분리 복구는 별도 절차다. 같은 디스크의 별도 파일은 디스크 장애, 랜섬웨어, 전체 서버 이미지 롤백에 대한 독립 사본이 아니다. GitHub의 집계 해시는 누락 감지는 가능하지만 회원별 파기 목록을 재구성하지 못한다.

## 보관 종료

로컬이라고 무기한 보관하지 않는다. 기존 `ErasureRetirementPlanner`는 읽기 전용 후보 판정기이며 자동 파일 삭제 기능은 아니다. 기존 32일은 검토 시작 기준이지 자동 만료일/법정 보관 기간이 아니다.

실제 보관 종료에는 과거 백업·binlog·수동 사본 소멸 확인, 완료 기록 확인, 복원 하한 유지, 파일 삭제와 독립 체크포인트 변경의 중간 실패 복구가 필요하다. 현재 append-only 체크포인트에 감소 건수를 임의로 기록하지 않는다. cron/find/파일 수정 시각만으로 대장 파일을 삭제하지 않는다.

## 인수 체크리스트

2026-09-09 최종 로컬 선택 테스트: API 81건 + batch 138건 = 219건, 실패/오류/건너뜀 0건. 이후 별도 승인으로 미니 PC의 새 임시 폴더에서 Linux 합성 검증 12항목도 통과했다. 전체 프로젝트 테스트나 운영 전환 인수 완료를 뜻하지 않는다.

Linux 검증은 일반 사용자, OpenJDK 21.0.12, ext4에서 실제 파일/디렉터리 `force`, 0700/0600, 링크 거부, 별도 JVM 잠금 경합, 손상/카탈로그 누락/마커 유실/같은 건수의 다른 내용에 대한 복원 전 검증 차단을 확인했다. GitHub 기준은 메모리 가짜 객체이고 실제 DB 복원이나 클라우드 접속은 수행하지 않았다. 강제 정전이나 운영 컨테이너 UID/bind mount 인수는 포함하지 않는다.
